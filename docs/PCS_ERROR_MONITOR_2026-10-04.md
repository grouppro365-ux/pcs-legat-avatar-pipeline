# Очереди ошибок и неизвестной доставки

Раздел теперь читает действующую Supabase pcs_failed_jobs, которую обрабатывает pcs-retry-worker v3. Предыдущая Neon failed_jobs не была связана с этим worker. Источники не объединяются по несовместимым идентификаторам.

Отдельная вкладка читает сохранённые PROCESSING попытки ручных сообщений CRM и AI-согласований из Neon messages. Она показывает идентификатор попытки, дату и клиента и открывает настоящий диалог. Автоматической отправки или ручного утверждения доставки эта вкладка не выполняет.

Обе очереди имеют страницы по 200 строк. REST-запрос идёт только с сервера после проверки администраторской сессии; service key не передаётся браузеру. В API не выдаются payload события и тексты сообщений. Строки ошибок ограничены и очищаются от распространённых форматов ключей/подключений. Ошибка чтения не выдаётся за пустую очередь; статус review_required виден явно.

Подтверждено: worker активен, cron pcs_trigger_retry_worker активен, service_role имеет SELECT на pcs_failed_jobs. Unit/UI тесты покрывают источники, авторизацию adapter, поля, страницы и ошибки. Реальные задания не запускались вручную, сообщения клиентам не отправлялись.

Открыто: кнопка ручного повтора не подключена к старому безусловному pcs-errors-api retry. Требуется проверить идемпотентность runtime обработки входящего Telegram-события и затем добавить условный enqueue с атомарным audit. Статусы resolved/retrying не переименовываются в подтверждённую доставку. Другие каналы и ошибки автоматической генерации остаются в общем backlog.
