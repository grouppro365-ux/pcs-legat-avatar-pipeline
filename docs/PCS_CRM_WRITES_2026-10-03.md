# CRM: редактирование и ручные задачи

Опубликованная сборка: https://grouppro365-ux.github.io/pcs-legat-avatar-pipeline/?release=20261003-crm-actions3. Глобальная кнопка Telegram проверена через getChatMenuButton. Vercel пока отдаёт предыдущую версию быстрых действий. После перехода на новый origin нужен повторный вход. Menu updater и gateway используют тот же адрес; обновление не отправляет клиентам сообщения.

## Подтверждённая архитектура

Проверка schema metadata существующей операционной Neon базы выполнена через Supabase pg_net и pcs_edge_runtime_config. Credentials оставались на сервере, не выдавались браузеру и не сохранялись в репозитории. contacts, tasks и audit_logs находятся в одной базе. tasks.contact_id ссылается на contacts.id. ID имеют тип text; поддержаны UUID и строковые ID. Supabase pcs_contacts/pcs_tasks не используются в этих операциях.

Редактор поддерживает реальные поля contacts: name, phone, username, language, city, country, budget, need, next_action, next_action_at, status и priority. Дополнительные поля старого редактора (WhatsApp/LINE/passport и другие) отсутствуют в этой Neon таблице; запись в выдуманные поля не включена. Документы договора продолжают храниться в существующем контуре договоров.

## Поведение

- Открытие редактора читает свежую карточку. PATCH отправляет только изменённые поля; отсутствующий срок следующего шага не превращается в автоматически назначенный.
- edit_version — точное updated_at::text с микросекундами. Сервер сравнивает её внутри UPDATE, без округления JS Date. При конфликте возвращает 409, форма сохраняет введённые данные.
- Статусы и приоритеты проверены против существующих enum ContactStatus/Priority. Изменение статуса CRM не подтверждает платежи и не меняет финансовые записи.
- contact identity, source, telegram_user_id и прочие неразрешённые поля нельзя изменить через этот маршрут.
- Изменение контакта и audit выполняются одним SQL statement. В audit сохраняются названия изменённых полей, без копирования паспорта, текста запроса или телефона.
- Создание задачи получает стабильный ID формы. Retry с тем же ID/данными возвращает существующую задачу; иной клиент или изменённые данные не получают чужую задачу.
- Завершение проверяет task ID вместе с contact_id. Повторное завершение не меняет дату и не создаёт второй audit.
- Все новые маршруты проходят существующую HMAC admin-проверку. JSON body ограничен 32 KiB. SQL values параметризованы; имена изменяемых колонок берутся только из фиксированного allowlist.

## Проверки и ограничения

Автоматические тесты покрывают partial edits, версии, формат/длину данных, admin auth, сохранение формы при конфликте, отсутствующий срок, строковые ID и повторные запросы. tests/crm-db-rollback.mjs генерирует проверку реального SQL: изменение контакта, устаревшая версия, создание/retry, завершение/retry, неверный владелец и rollback изменения при ошибке audit. Запрос выполнился на действующей схеме (HTTP 200, command DO); все синтетические записи откатились в subtransaction.

Production UI E2E с пользовательским входом и native Telegram остаётся непроверенным. Ручные задачи подключены; scheduler, автоматические follow-up и escalation остаются в master backlog. Быстрые кнопки HOT/ожидания/потери/оплаты открывают редактор для проверки и используют тот же PATCH; legacy /action endpoint остаётся заблокированным. Готовность к оплате записывается как следующий шаг, без выдуманного enum и без подтверждения финансовой операции. Общий проект не завершён.
