# Защита обычных маршрутов редактирования брони

Проверка обнаружила, что application-status и application-save могли обойти интерфейс подтверждения фактов аренды. Manager v12 запрещает создание booking сразу в SERVICE_IN_PROGRESS/COMPLETED, изменение уже активной/завершённой/отменённой брони и изменение её категории. Отсутствующая категория существующей брони сохраняется как booking. Несуществующая заявка возвращает 404. Проверка состояния повторяется внутри условного UPDATE; отсутствие изменённой строки не возвращает успех.

Штатный application-rental-phase и проверка фактов в pcs-contract-api не изменены. Ручное подтверждение выдачи/возврата продолжает проходить через центр договоров. Non-booking workflows сохраняют обычный маршрут статуса. Оплаты, права других ролей, полный аудит и production Telegram E2E остаются отдельными открытыми задачами.

90 regression tests прошли. Проверены попытки подделать фазы через оба generic маршрута, новые заявки с подставленным статусом, locked states, смена категории, отсутствующий ID и конфликт состояния перед UPDATE. Тестовые данные синтетические; сообщения реальным клиентам не отправлялись. Схема базы не менялась.
